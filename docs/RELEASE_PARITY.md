# Контракт функционального паритета релизов

Актуально на 8 сентября 2026 года.

Этот документ задаёт обязательное правило разработки ЛЕКАЛО: пользовательское нововведение не считается завершённым, пока оно не доступно и не проверено во всех поддерживаемых вариантах приложения. Слова «должно», «обязательно» и «нельзя» ниже являются релизными требованиями, а не рекомендациями.

## Поддерживаемые варианты приложения

ЛЕКАЛО использует один общий frontend и один набор алгоритмов:

| Вариант | Как получает общий frontend |
|---|---|
| Web / устанавливаемая PWA | GitHub Pages публикует файлы из корня ветки `main` |
| Телефон и планшет | та же Web/PWA, интерфейс меняется адаптивными CSS-слоями, а не отдельной логикой |
| Windows | `desktop/Build-Desktop.ps1` побайтово копирует общий frontend в portable bundle и открывает его в защищённой WebView2-оболочке |
| Будущий Android / RuStore | Android-оболочка должна встраивать тот же общий frontend и предоставлять только системные адаптеры Android |

Общий runtime состоит из `index.html`, `manifest.webmanifest`, `sw.js`, каталогов `assets/` и `src/`. Формулы построения, схемы мерок, проверки, экспорт, справка, переводы и пользовательские предупреждения живут только здесь. Создавать их копии внутри Windows- или Android-оболочки нельзя.

## Неподлежащие разделению функции

Следующие возможности обязаны оставаться одинаковыми на всех платформах:

- каталог и статусы выкроек;
- мерки, допустимые диапазоны, взаимные ограничения и формулы построения;
- параметры ткани, фасона и безопасные регуляторы A/B/C;
- геометрическая валидация, предупреждения о примерке и производственные ограничения;
- форматы и содержание проектов, профилей, шаблонов и библиотек;
- PDF, SVG, DXF, JSON и размерные пакеты, если платформа позволяет сохранить файл;
- русская и английская локализация;
- темы, доступность, клавиатурное и сенсорное управление;
- раздел «Помощь», его темы, поиск, контекстные переходы и честные границы возможностей;
- правила приватности, отсутствие скрытой аналитики и отправки мерок без явного решения владельца.

Размер окна, способ выбора файла или системная кнопка «Поделиться» не должны менять смысл результата. Одинаковые входные данные обязаны давать одинаковую геометрию и одинаковые экспортные данные независимо от оболочки.

## Где реализуется новое

Новую продуктовую функцию сначала реализуют в общем frontend:

- логика и геометрия — `src/core/`;
- экран или компонент — `src/ui/`;
- стили — `assets/css/app.css` либо другой общий файл из `assets/`;
- точка подключения — общий граф импортов от `assets/js/main.js`;
- текст помощи — `src/ui/help/helpContent.js`;
- локализация — общий модуль i18n и двуязычный контент функции;
- тесты — `tests/`.

Файлы из `docs/` предназначены для чтения человеком и не входят в Windows runtime. Пользовательская справка не должна во время работы загружать Markdown из `docs/` или внешний сайт: нужное содержание хранится в общем frontend и доступно без сети.

Если runtime-файл добавлен за пределами `assets/` или `src/`, необходимо явно добавить его одновременно:

1. в список упаковки `desktop/Build-Desktop.ps1`;
2. в `CORE` внутри `sw.js`, если он нужен офлайн;
3. в будущий список Android assets;
4. в автоматическую проверку зеркала frontend.

Предпочтительно не расширять этот список и держать продуктовый runtime в общей структуре.

## Обязательное обновление справки

Каждое нововведение оценивается на необходимость новой или изменённой инструкции. Если пользователь получает новую кнопку, настройку, формат, ограничение или рабочий сценарий, в том же изменении обязательно:

1. обновить соответствующую тему в `src/ui/help/helpContent.js` либо добавить новую тему;
2. добавить контекстный переход к ней с нужного пользовательского экрана;
3. сохранить полный смысл на русском и английском языках;
4. проверить поиск по практическим формулировкам пользователя;
5. обновить связанный документ в `docs/`, если изменился внешний рабочий процесс;
6. включить новые файлы справки в offline-кэш;
7. добавить или изменить автоматические тесты справочного контракта.

Справка должна описывать реальную выпущенную функцию. Документировать будущую возможность как уже работающую нельзя.

## Версии и offline-кэш

Версия продукта задаётся в `src/core/app/version.js` и должна совпадать с `package.json`. Для Windows тот же номер отражается в трёх assembly-атрибутах `desktop/LekaloDesktop.cs` и в `desktop/app.manifest`; `tests/release_parity.test.js` блокирует рассинхронизацию этих значений.

При каждом релизе, меняющем общий runtime, обязательно:

- увеличить семантическую версию приложения;
- увеличить `BUILD` в `sw.js`, чтобы установленная PWA и постоянный профиль Windows не удерживали старый offline-кэш;
- добавить каждый новый модуль из публичного графа импортов в `CORE`;
- выполнить fresh-online запуск, обновление существующего профиля и offline-перезапуск;
- убедиться, что в интерфейсе, ZIP, EXE, release tag и документации указан один выпуск.

`manifest.webmanifest` не содержит стандартного номера версии приложения. Его изменяют только при изменении имени, описания, иконок, `start_url`, `scope`, display-режима или других PWA-метаданных.

Версии отдельных модулей выкроек и форматов хранения независимы от версии приложения. Их нельзя повышать только из-за изменения интерфейса или справки: это делается при реальном изменении формул, схемы или совместимости данных и сопровождается миграционными тестами.

## Критерии Done для любого нововведения

Функция считается готовой только если одновременно выполнено всё перечисленное:

1. Реализация находится в общем frontend, без отдельной продуктовой копии для оболочки.
2. Функция доступна со всех относящихся к ней экранов и не теряется после смены языка, темы, размера окна или маршрута.
3. Русский и английский тексты полны; доступны понятные подписи, фокус и управление клавиатурой/касанием.
4. Справка и постоянная документация обновлены вместе с кодом.
5. Новые runtime-файлы входят в offline `CORE`, а номер кэша увеличен.
6. Детерминированные и контрактные тесты проходят локально и в CI.
7. На телефоне, планшете, split-screen и desktop нет наложений, обрезанного текста и горизонтального переполнения страницы.
8. Общий frontend работает онлайн, после обновления существующей PWA и при отключённой сети.
9. `Build-Desktop.ps1 -Clean` подтверждает точное зеркало frontend и завершает реальный smoke-тест упакованного EXE.
10. Windows-сценарий функции проверен внутри готового bundle, а не только в обычном браузере.
11. GitHub Pages проверен после фактического развёртывания нужного commit SHA.
12. Релизные номер, changelog, контрольная сумма и ссылки соответствуют опубликованным артефактам.

Отсутствие отдельной оболочки освобождает только от проверки этой ещё не существующей оболочки. После появления Android-проекта его сборка и реальные устройства становятся обязательной частью Done.

Контрольные области просмотра:

## Минимальные команды перед релизом

```powershell
git diff --check
npm.cmd run check
.\scripts\Test-LocalServer.ps1
.\desktop\Build-Desktop.ps1 -Clean
```

Сборка Windows без smoke-теста не является релизным подтверждением. Tag-workflow должен загружать ZIP и соответствующий `.sha256`, а его результат должен быть успешным.

После публикации требуется проверить фактический Pages deployment, текущий `BUILD` в `sw.js`, доступность всех `CORE`-ресурсов и браузерную матрицу на публичном URL. Отчёт обязан отличать локальные тесты от подтверждённой live-проверки.

## Допустимые platform-only различия

Различие разрешено только там, где операционная система предоставляет другой механизм:

- Windows: рамка окна, F11, single-instance, WebView2 Runtime, системный SaveFileDialog и открытие внешней ссылки в системном браузере;
- Web/PWA: браузерная установка, Service Worker, браузерные file picker/download и политика обновления PWA;
- телефон/планшет: адаптивная компоновка, нижняя навигация, safe-area, экранная клавиатура, touch/stylus-поведение;
- Android: системная кнопка Back, Storage Access Framework, Share sheet, жизненный цикл Activity, WebViewAssetLoader, подпись APK/AAB и магазинное обновление.

Platform-only адаптер может менять способ выполнения, но не набор пользовательских данных, правила построения, результат экспорта или содержание справки. Для функции, недоступной из-за реального ограничения платформы, должен существовать общий безопасный fallback и явное объяснение пользователю.

Каждое исключение фиксируется в изменении по шаблону:

```text
Различие:
Затронутые платформы:
Причина ограничения платформы:
Общий fallback:
Автоматическая и ручная проверка:
Ответственный и условие пересмотра:
```

Незадокументированное различие считается ошибкой релиза.

## Ворота будущего Android-релиза

Android-оболочка принимается только если она упаковывает frontend того же commit и версии, которые прошли Web/PWA и Windows-проверки. Дополнительно проверяются:

- хэш встроенного frontend либо воспроизводимое сопоставление файлов с общим источником;
- запуск без сети до первого обращения к сайту;
- импорт, экспорт, Share, Back и восстановление после пересоздания Activity;
- реальный телефон, планшет, foldable и Chromebook;
- сохранение данных при разрешённом обновлении и явное удаление по запросу пользователя;
- один постоянный package id и один защищённый production signing key.

Разработка отдельной Android-геометрии, отдельного каталога выкроек или сокращённой справки запрещена: это создало бы вторую несовместимую версию продукта.
